# Phase 3, Plan 06 [windows]: Rename the repository and ship 4.0.0

## Phase Goal

ROADMAP Goal line (verbatim): "PrintInvoicer becomes Billament everywhere (code, app, PDFs, scripts, docs, data folders
and the GitHub repository), existing users keep every job and finalized invoice through a one-time safe move of their
data, and the result ships as 4.0.0, so later phases are built under the new name from the start."

The Goal line is not a user story; this restates the part this plan delivers without adding scope (run
`/gsd-mvp-phase 3` to replace it with a canonical story if wanted):

**As a** 3.7.0 user, **I want** my app's update bar to tell me about 4.0.0 after the repository is renamed, **so that**
I find the new version without looking for it.

This plan is the rest of the D-21 checklist: the final search once more, the repository rename (D-14, a manual step),
the redirect checks (D-16), and the 4.0.0 release (D-05).

**Path names in this plan:** the new `Billament.*` names. The old repository name appears only in the redirect checks.

4.0.0 with the existing release workflow, and confirms an installed 3.7.0 sees the update.

Where D-16 is verified: in this plan. RESEARCH assumptions A1 (the old API address redirects with the path
`/releases/latest` kept) and A2 (the old web address redirects to the new releases page) could not be tested during
research, because the cloud container cannot reach GitHub for this repository and the rename has not happened yet. No
earlier plan verifies them; this plan is the gate, in two steps:
- before publishing: Task 2 step 3 (curl on the old API address right after the rename: 301 or 307, a `location:`
  ending in `/releases/latest`, 200, and `"tag_name": "v3.7.0"` in the body), Task 2 step 4 (the old web address) and
  Task 2 step 5 (Check now in an installed 3.7.0 gets through to GitHub, so the app's own client follows the redirect);
- after publishing: Task 3 step 6 (Check now in an installed 3.7.0 shows 4.0.0, and Download reaches the Billament
  releases page).

What to do if 3.7.0 does not find the update (D-16): 3.7.0 cannot be changed, so the plan stops before the one-way
step. If any check in Task 2 fails, nothing is tagged or published until the user replies with one choice (Task 2
step 7), and the reply is recorded:
- `wait`: the repository stays renamed, nothing is published, and the run ends; the checks are run again later.
- `roll back`: the user renames the same repository back to PrintInvoicer and publishes nothing. This is the rollback
  path for the rename; it renames the existing repository, so it is not the new repository the prohibition forbids.
  NAME-05 stays open and the next try is planned as a gap (`/gsd-plan-phase 3 --gaps`).
- `publish with fallback`: 4.0.0 is released knowing 3.7.0 will not show the update bar (or its Download will not land
  on the releases page). The notice from plan 03-04 (the README "Renamed from PrintInvoicer" section, the release-notes
  paragraph, old web links) is then the only way 3.7.0 users find it, and NAME-05 and success criterion 4 are recorded
  as "fallback accepted by the user", never as passed.
Task 3 starts only after "checks passed" or a recorded `publish with fallback` reply (its precondition). There is no
rollback once 4.0.0 is published (D-05): if Task 3 step 6 fails after the Task 2 checks had passed, NAME-05 is recorded
as failed and the user plans a gap. In every case, never create a repository with the old name to work around a
failure, because that ends every redirect.
