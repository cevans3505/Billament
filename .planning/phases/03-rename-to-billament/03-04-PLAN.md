# Phase 3, Plan 04 [cloud]: Upgrade notes, the old-install cleanup and the final search

## Phase Goal

ROADMAP Goal line (verbatim): "PrintInvoicer becomes Billament everywhere (code, app, PDFs, scripts, docs, data folders
and the GitHub repository), existing users keep every job and finalized invoice through a one-time safe move of their
data, and the result ships as 4.0.0, so later phases are built under the new name from the start."

The Goal line is not a user story; this restates the part this plan delivers without adding scope (run
`/gsd-mvp-phase 3` to replace it with a canonical story if wanted):

**As a** 3.7.0 user who sees the 4.0.0 update bar, **I want** the release notes, the read-me in the zip and the README
to tell me the same short story (run Billament.exe, my data moves once after a safety copy, delete the old exe), **so
that** I upgrade without fear. **As the** maintainer, **I want** `publish.ps1` to retire my old PrintInvoicer install
and a final search to prove the old name is gone except where it must stay, **so that** the rename is complete.

**Path names in this plan:** every path uses the new `Billament.*` names. Old-name strings written here (the cleanup
in publish.ps1, the comment on `UpdateService.Repository`, the notes) are deliberate (D-19); no bulk replacement runs.

Output: README rename section, Read me section, release notes paragraph, UpdateService comment, publish.ps1 cleanup,

## Decisions and assumptions recorded (overturnable by the user)

- **(d) Restoring a pre-4.0 backup** (user decision D-25, 2026-11-02, overturning the earlier docs-only choice):
  03-03 makes Billament apply the same folder rewrite right after a restore, so `BackupFolder` and `InvoiceFolder`
  values inside `Documents\PrintInvoicer` point at the same place under `Documents\Billament`. The README and Read me
  say so instead of telling the user to set the folders again.
- **publish.ps1 removes the old install only after the new one is in place**, and only the exact default old program
  folder `%LOCALAPPDATA%\Programs\PrintInvoicer`, so a failed publish never leaves you without a working program
  (RESEARCH publish.ps1 design). RESEARCH A5 (`Get-Process -Name` with two names and `SilentlyContinue` ignores names
  with no process in Windows PowerShell 5.1) is checked by running the script in plan 03-05.
- **The upgrade paragraph stays in release.yml's draft notes for every 4.x release**, because a 3.7.0 user may skip
  straight to a later 4.x.
- **D-16 is verified by the 03-06 gate, not by this plan.** RESEARCH assumption A1 (after the rename,
  `GET /repos/cevans3505/PrintInvoicer/releases/latest` answers 301 or 307 with a `Location` that keeps
  `/releases/latest`, then 200 with the release reply) could not be tested during research: the cloud container cannot
  reach GitHub for this repository, and the repository is not renamed yet. This plan only explains the redirect (Task 1
  step 1) and writes the fallback notice (Task 1 steps 2 to 4). The verification runs in plan 03-06, which the user does
  on GitHub and Windows:
  - Task 2 step 3, right after the user renames the repository and before 4.0.0 is published: curl on the old API
    address must show 301 or 307, a `location:` ending in `/releases/latest`, then 200, and the body must hold
    `"tag_name": "v3.7.0"` (the field 3.7.0 reads). Task 2 step 4 checks the old web address ends at the Billament
    releases page (RESEARCH A2).
  - Task 3 step 6, after 4.0.0 is published: an installed 3.7.0 must say `Version 4.0.0 is available. You have 3.7.0.`
    on Check now, and its Download button must reach the Billament releases page.
  - If the redirect does not reach the release: 3.7.0 cannot be changed, so it will not show the update bar. Plan 03-06
    then stops before anything is tagged or published (its Task 2 step 7) until the user replies "wait" (check again
    later), "roll back" (rename the same repository back to PrintInvoicer and publish nothing) or "publish with
    fallback". The fallback is the notice this plan writes: the README section "Renamed from PrintInvoicer" with its link
    to the latest release (old web links lead to it through the redirect) and the upgrade paragraph in the release notes.
    3.7.0 users then find 4.0.0 only when they visit the old or new GitHub page, and NAME-05 is recorded as "fallback
    accepted by the user", not as passed. The user records the result and the reply in 03-06-SUMMARY.md or 03-UAT.md,
    and never creates a repository with the old name to work around it, because that would end every redirect (03-06
    prohibition).
