# Phase 3, Plan 02 [cloud]: The one-time safe move of the data folders

## Phase Goal

ROADMAP Goal line (verbatim): "PrintInvoicer becomes Billament everywhere (code, app, PDFs, scripts, docs, data folders
and the GitHub repository), existing users keep every job and finalized invoice through a one-time safe move of their
data, and the result ships as 4.0.0, so later phases are built under the new name from the start."

The Goal line is not a user story; this restates the part this plan delivers without adding scope (run
`/gsd-mvp-phase 3` to replace it with a canonical story if wanted):

**As a** user upgrading from 3.7.0, **I want to** start Billament and find every job and finalized invoice where it
was, **so that** the rename costs me nothing; and if the move cannot finish, **I want** a plain message that tells me
where my data is and that nothing was lost.

This plan delivers NAME-03 (D-06 to D-12): the move logic in Core with Linux tests, the App wiring before the database
opens, the AUDIT tags and the AUDITING.md rows. Plan 03-03 adds the rewrite of the two folder settings (D-13) inside the
same `Run`, and the handling of old backup names.

**Path names in this plan:** every path uses the new `Billament.*` names that exist after plan 03-01. The old folder
and file names appear only as values the code moves (constants in `DataFolders`, test data); they are deliberate.

<objective>
Where it runs: [cloud] (Core code and Linux tests; the App half is compile-checked here and run on Windows in 03-05).

Add `DataFolderMigration` to Core: a static `Run(DataFolders, DateTime, FileOps?)` that, once, backs up the old
database, renames the two old data folders to the new names and renames the database file, and never deletes,
overwrites or merges anything; call it from `App.OnStartup` before the database opens; cover the happy path, the

Purpose: existing users keep all their data through the rename (ROADMAP success criteria 2 and 3).
Output: `src/Billament.Core/Data/DataFolderMigration.cs`, `tests/Billament.Tests/DataFolderMigrationTests.cs`, the
start-up change in `App.xaml.cs`, AUDITING.md rows and "There are 35 tags".

## Decisions and assumptions recorded (overturnable by the user)

The orchestrator asked for these to be stated as assumptions. Each one is the RESEARCH default unless marked.

- **(a) A failed Documents move stops start-up.** `App.MoveOldData` shows the plain message (which names the folder
  that holds the data and says nothing was lost), saves the details with `ErrorReport.Save`, and calls `Shutdown(1)`
  before any `new Database`, so no `Documents\Billament` is created and the next start retries cleanly (RESEARCH Open
  Question 1).
- **(b) A failed `%LOCALAPPDATA%` move is not fatal, and the user is told nothing.** That folder holds only the window
  layout, the update-check answer and old error files. The details go to the error file. Side effect, accepted: the
  error file itself is written under `%LOCALAPPDATA%\Billament`, so the old local folder is then skipped for good
  (D-08) and the app starts with a default window layout.
- **(c) An unrelated existing `Documents\Billament` blocks the move (D-08) and a notice is shown.** Condition: the old
  folder holds `printinvoicer.db` and the new folder holds neither `billament.db` nor `printinvoicer.db`. The notice
  says where the old data is and how to use it (close Billament, rename or move the new folder, start again). It shows
  once: that first start creates `billament.db` in the new folder.
- **Backup first, strictly (D-07).** The safety copy is made before anything moves, including the `%LOCALAPPDATA%` pair.
  If the copy fails, nothing moves (the local pair is reported `NotTried`). Side effect, accepted as in (b): the error
  file written for that failure creates `%LOCALAPPDATA%\Billament`, so the old local folder is skipped from then on
  (window layout and update-check answer only).
- **Backup place and name (CONTEXT discretion):** `DatabaseBackup.Manual` into `Documents\PrintInvoicer\Backups` with
  label `pre-rename`, so it moves with the data to `Documents\Billament\Backups\billament-<yyyy-MM-dd-HHmmss>-pre-rename.db`.
  It is never pruned (its name does not match the daily pattern). It always goes into the data folder's own Backups
  folder, even when Settings names another backup folder. Plan 03-04 writes this location into the README and Read me.
- **How the move is done (CONTEXT discretion):** `Directory.Move` of each old folder to its sibling new name (same
  parent, so a rename on the same volume, atomic on NTFS); no copy fallback, so no partial copy can exist. A junction
  at the old name is renamed as a link (RESEARCH A3, accepted).
- **Only the main database file is renamed** (a deliberate narrowing of RESEARCH Pattern 1 step 6, which also listed
  the `-journal`, `-wal` and `-shm` siblings). Reason: the code never turns on WAL (RESEARCH verified no `journal_mode`
  pragma), and a hot rollback journal makes SQLite refuse the read-only open that the safety copy uses, so the copy
  fails and nothing moves; the move therefore only ever runs when no journal needs replaying, and a leftover cold
  journal is ignored by SQLite. Renaming siblings would add half-renamed states for no gain.
- **No marker file.** "The new folder exists" is the run-once check (it is also D-08). The repair rule covers the one
  state that check alone would strand: `printinvoicer.db` inside `Documents\Billament` with no `billament.db`.
- **A successful move is silent.** No dialog on success; the README and Read me (plan 03-04) explain the move.
