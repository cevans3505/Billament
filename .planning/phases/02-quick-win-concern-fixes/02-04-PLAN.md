## Phase Goal

ROADMAP Goal line (verbatim): "The concerns with the best benefit for the cost (triage score 2.0 and above) are fixed in
score order, so releases can be checked, invoices already sent are guarded by a test, and paths, file names and update
checks are handled safely."

The Goal line is not a user story; the stories below restate the parts this plan delivers without adding scope. Run
`/gsd-mvp-phase 2` to replace them with canonical stories if wanted.

**As a** PrintInvoicer user, **I want** invoice PDFs named safely whatever I type as the job title or invoice number,

when a path holds a quote or space, **so that** a path can never turn into extra Explorer switches.

FIX-06 is the tracer: its slice crosses Core, App and tests and carries the most risk (it decides every invoice file
name). It runs in Wave 3 because it edits AUDITING.md after plan 02-03 and keeps the tag count 02-03 set (27).

## Which invoice names change (decision, recorded)

Before this phase `InvoicePdf.Write` named a PDF `{prefix} {number} {Safe(title)}{suffix}`. In the Windows app, `Safe`
turned `" < > | : * ? \ /` and the characters U+0000 to U+001F into `-`, then trimmed whitespace from both ends; the
invoice number went in as typed. Now both parts go through `SafeFileName.Clean` (title limit 60, number limit 30). A
PDF keeps exactly its old name when, and only when, both parts keep their old text.

**Title.** The title keeps its old text if all six hold, and gets a new one otherwise:

1. It has no character from U+007F to U+009F and no unpaired surrogate (kept before; each now becomes `-`).
2. It has no run of two or more dots (now one dot).
3. After the forbidden and control characters become `-`, and ignoring plain spaces at either end, it neither starts
   nor ends with a dot or with another whitespace character such as a no-break space (the old code trimmed every
   whitespace character and no dot; the new code trims plain spaces and dots).
4. It is not empty or whitespace only (that used to give `Invoice 2026-001 .pdf`; now `Invoice 2026-001 untitled.pdf`).
5. Trimmed, it is at most 60 UTF-16 chars (a longer title is now cut, never splitting a character).
6. Its part before the first dot, with trailing spaces removed, is not a Windows device name (CON, PRN, AUX, NUL, COM0
   to COM9, LPT0 to LPT9, the superscript COM and LPT forms, CONIN$, CONOUT$, in any case); such a title now starts
   with `_`.

**Invoice number.** The number keeps its old text if it already equals `SafeFileName.Clean(number, 30)`: at most 30
UTF-16 chars, not empty, none of `< > : " / \ | ? *`, no control character or unpaired surrogate, no run of two or more
dots, no space or dot at either end, and its part before the first dot is not a device name. Draft numbers
(`draft yyyy-MM-dd`) and numbers the counter makes with the default prefix (`{yyyy}-` and three digits, such as
`2026-001`, `AppSettings.FormatInvoiceNumber`) always keep their text. A number holding `/`, `\`, `:` or another
forbidden character never gave a normal PDF in the invoice folder before (it pointed into another folder, or Windows
refused or misread the name), so no working name is lost there.

**Effect and decision (Claude's discretion, recorded).** File names do not feed pricing: `PricingCalculator`,
`PriceSnapshot` and the stored `FinalizedTotal` never read them, so the rule that a finalized invoice's totals never
change is not touched. The only effect of a changed name is that regenerating that invoice writes the PDF under the
new name and leaves the earlier PDF beside it. Nothing is deleted or renamed, because renaming or deleting earlier PDFs
would be new file access outside FIX-06. This is accepted for the cases above, which are unusual titles and typed
numbers; a title over 60 chars is the likeliest real one. Task 1 pins both sides of the boundary with tests, and the
SUMMARY copies this section under `## Which invoice names change`.
